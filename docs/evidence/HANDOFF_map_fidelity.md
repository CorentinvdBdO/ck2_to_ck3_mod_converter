## 1. For lane `map-ui` — take these four facts before writing a locator

1. **Coordinate frame** (`verified`, `scripts/map_fidelity_locators.py`,
   400 provinces): `position = { x  height  z }`. `x` is the `provinces.png`
   **column**; `z` is measured from the **bottom** of the image, so
   `z = image_height − y_top`. Median distance from the province centroid in
   vanilla is 4.3 px in x and 4.6 px in z; read top-origin instead and you are
   out by a median of 2,983 px. Same convention as CK2 `positions.txt` y.
2. **Rotation is yaw only.** All 82,572 vanilla instances have
   `rotation = { x y z w }` with **x = z = 0**. From a CK2 slot rotation θ
   (radians) write `{ 0, sin(θ/2), 0, cos(θ/2) }`. Faerûn leaves θ = 0 in
   80–100 % of slots, so most of ours will be `{ 0 0 0 1 }`.
3. **Height and scale need no work.** `position.y = 0.000000` in all but 78 of
   82,572 instances (`clamp_to_water_level = yes` does it), `scale = { 1 1 1 }`
   in all but 125.
4. **Eight files, not one**, or the object keeps drawing at the vanilla
   province's place (playtest item 7). Vanilla instance counts, all keyed by
   province id:

   | `name=` | file | instances | layer | `clamp_to_water_level` |
   |---|---|---|---|---|
   | `buildings` | `building_locators.txt` | 11,297 | `building_layer` | yes |
   | `special_building` | `special_building_locators.txt` | 11,297 | `building_layer` | yes |
   | `siege` | `siege_locators.txt` | 11,297 | `unit_layer` | no |
   | `activities` | `activities.txt` | 11,297 | `activities_layer` | no |
   | `combat` | `combat_locators.txt` | **12,065** | `unit_layer` | yes |
   | `unit_stack_player_owned` | `player_stack_locators.txt` | **12,065** | `unit_layer` | yes |
   | `unit_stack_other_owner` | `other_stack_locators.txt` | 8,906 | `unit_layer` | yes |
   | `unit_stack` | `stack_locators.txt` | 4,348 | `unit_layer` | yes |

   11,297 = land provinces; the 12,065 sets **also cover water**, so a
   land-only generator leaves naval combat and player fleets unanchored.
   `layers.txt` / `game_object_layers.txt` declare the layer names —
   `replace_path` is not needed, a same-named file overrides.

**Better than centroids, where it is cheap:** for a county's capital barony use
CK2 `positions.txt` slot 0 (the CK2 binary's own "capital location"), and for a
coastal `city_holding` use slot 4 (its "port location", 36.1 % of which sit on
water, i.e. on the harbour). Everything else: centroid. `overrides/barony_seeds_ck2positions.csv`
already holds 3,619 such points in canvas pixels, generated by
`scripts/barony_seeds_from_ck2_positions.py`.

**Also for map-ui, from §1.3 and §4.3 of the doc:** the zoomed-out paper map of
playtest item 5 is one texture, `gfx/map/terrain/flat_maps/flatmap.dds`
(21 MB), and the map's overall colour comes from
`gfx/map/terrain/colormap.dds` (9216×4608 DXT5). CK2 ships the exact analogue
at `map/terrain/colormap.dds`, so a resample is the cheapest possible
de-Europe-ing of the map.

## 2. For a future lane `map-paint`

* **The runtime terrain format is `gfx/map/terrain/detail_index.tga` +
  `detail_intensity.tga`, not the masks.** `verified`: index channels are
  ordinals into `materials.settings` declaration order, intensity channels sum
  to exactly 255, and 49.1 % of vanilla's own used channels name a material
  whose shipped mask is 0 at that pixel — the masks are map-editor input and
  are stale. A converter can write the pair directly; no editor, exactly like
  `ck2ck3.map.packed_heightmap`.
* **We currently ship no `gfx/map` at all**, so Faerûn renders with vanilla
  Europe's paint stretched over it. This is the biggest single cause of "ugly
  map".
* `scripts/prototype_terrain_masks.py` has a first CK3-terrain-key → vanilla
  material table and builds the pair for a 2048² tile. Using existing vanilla
  materials means no new `.dds` and automatic colour/tiling consistency.
* Size, extrapolated to 8320×6784 (`terrain_paint_sizing.csv`): the index map
  is 8 MB RLE, the intensity map is 206 / 173 / 81 MB at 256 / 16 / 4 blend
  levels, and uncompressed either is 226 MB. The generated mod is 143 MB today.

## 3. For lane `baronies`, if it is ever reopened

CK2's seven `positions.txt` slots are distinct enough to reseed the Voronoi —
median 4 distinct in-county slots, 98.3 % of counties with ≥ 2, spread ≈ 0.94
county radii — and doing so would move **28.4 %** of baronies out of their
current cell (median shift 23 km). But only slots 0 and 4 mean anything CK2
documents; the other five are rendering anchors. Recommendation in
`docs/map_fidelity.md` §2: adopt slot 4 → coastal city barony, keep slot 0 →
capital, and expose the rest only as pre-filled rows for human review.

## 4. Decisions a human has to make

1. **Terrain-paint size.** Does the generated mod carry 89–452 MB of
   `detail_*.tga`? Two cheap experiments settle most of it and both need a game
   launch, which this lane was not allowed to do: (a) does CK3 accept **RLE**
   TGA for these two files, and (b) may they be **smaller than
   `provinces.png`** (half resolution quarters the bill; the shader samples in
   UV space, and vanilla being province-sized may be convention, not a rule).
2. **`resolution_factor = 1 → 2`.** Our heightmap Nyquist is 0.337 cycles/km
   against vanilla's 0.674, so at 1× we can never carry vanilla's finest half
   of the detail spectrum. Switching is one config line and roughly quadruples
   the heightmap bytes.
3. **Isotropic noise or real structure.** The prototype matches vanilla's
   amplitude *and* its `f^−2.0` spectrum, and still reads as gravel next to
   vanilla's dendritic valleys (`sword_coast/zoom_after.png` vs
   `zoom_vanilla_1x.png`). Ridged-multifractal or hydraulic erosion is an **L**,
   and it is a look call, not a correctness one.
