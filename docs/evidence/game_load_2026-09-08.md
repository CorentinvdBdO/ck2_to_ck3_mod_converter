### The two things attempt 3 taught

1. **A localisation key must be ASCII.**
   `localization_reader.cpp:445: Invalid character in key name 'Bjӧrn'` × 251.
   Vanilla agrees: 0 of its 55 948 name keys hold a non-ASCII byte, and its own
   north-Germanic list spells Björn `BjO_rn`, Andrés `AndrE_s`, Åke `A__ke`,
   with the accented spelling only in the loc value. The characters it does use
   in a name key are letters, digits, `_` and `-` (997 hyphens); an apostrophe
   also passes (571 of ours drew no complaint).
2. **Every vanilla region name has to be re-declared, not just the graphical ones.**
   `map_data/geographical_regions` is a `replace_path`, so **all 592** vanilla
   regions vanish. Vanilla scripts, GUI and achievements name them: 7,992
   `PostValidate of trigger 'geographical_region' returned false`, and one of
   them — `dlc_fp1_region_core_mainland_scandinavia`, looked up twice by the
   frontend — returned a null that became the access violation.

## §6 How to reach `In Game` at all

`Setting idler 'Frontend'` is the **main menu**. Nothing in a plain launch starts a
game, so `--marker "Setting idler 'In Game'"` without `--args "-test"` can only
time out even on a perfectly healthy mod: `-test` is the launch argument that
starts the default bookmark (and then runs every `tests/*.txt`), which is exactly
what `../claudespace/scripts/ck3_test.sh` passes
(`ck3_test.sh:131`). Attempt 3 timed out for that reason *as well as* crashing.
Every attempt from 4 on adds `--args "-test"`.

### The standing hypothesis for attempt 4's crash

The `loc` step turns a CK2 text code it cannot map onto a CK3 built-in into
`[ROOT.Char.Custom('GetFoo')]`, because that is what the code **is** in CK2: a
customizable localisation. Nothing ports
`Faerun/localisation/customizable_localisation/` yet, so all **795** distinct
names in **4,068** generated lines are dangling, and CK3 says
`jomini_custom_text.h:94: Object of type 'character' is not valid for 'VampName'`.
34 of those are the last lines written before the access violation.

Fix (g) made this worse by design: `vampire_collective_noun` and
`vampire_prefix` now copy `vampire`'s text, which *is* one of these calls
(`localization/english/fae_faerun_misc_l_english.yml:85-87`), so each affected
culture went from one unresolvable call to three.

`scripts/bisect_strip_custom_loc.py` rewrites every such call in a generated mod
to a plain `<Name>` (and `--restore` undoes it) so a launch can confirm or clear
the hypothesis without a converter change.

## §8 Fix (h), after attempt 4

`[loc] custom_loc` — a new policy key, defaulting to `marker`:

| value | a CK2 customizable-localisation code becomes |
|---|---|
| `call` | `[<scope>.Custom('name')]` — the CK3 spelling of the same feature, but the name must exist in `common/customizable_localization` |
| `marker` (default) | `<!CK2:<code>!>` — the same visible marker the converter uses for every CK2 construct with no CK3 home |

Nothing emits `common/customizable_localization`, so `call` produced 4,068 lines
naming 795 things CK3 does not know. After the switch **239** `Custom()` calls
remain, and all six names in them — `DaughterSon`, `MotherFather`,
`MistressMaster`, `LassLad`, `QueenKing`, `SisterBrother` — are **CK3 vanilla**
custom localisations from the mapping table in `docs/loc_codes.md`, so those
resolve.

Cost: text-code coverage drops 94.0 % → 91.0 %, honestly — a call to a name
nothing defines was never a conversion. `configs/faerun.toml` carries the
switch and the reason.

`scripts/bisect_strip_custom_loc.py` does the same edit to an already-generated
mod (and `--restore` undoes it) for bisecting without a converter change.

## §10 Fix (i), after attempt 5

`[loc] named_scope` — the sibling of `custom_loc`, defaulting to `marker`.
Everything the converter resolves itself starts the CK3 chain with a scope word
it chose (`ROOT.Char`, `THIS.Char`, `PREV.Char`, `GetPlayer`); **any other head
is a saved scope**, and there are three sources:

| source | in | out under `reference` |
|---|---|---|
| a CK2 event target | `[relic_hunter.GetTitledFirstName]` | `[relic_hunter.GetTitledFirstName]` |
| a CK2 `From` chain (CK3 has no `FROM` loc scope) | `[From.GetFirstName]` | `[ck2_from.GetFirstName]` |
| a CK2 chain word used as the head | `[Culture.GetName]` | `[Culture.GetName]` |

Under the new default all three become `<!CK2:…!>`, and the run log reports
`named_scope_markered = 64803` over `named_scope_names = 2566` — the debt the
event port clears. `tests/test_loc_step.py` now asserts the invariant directly:
**no generated localisation line may open a chain with a head the converter did
not choose itself.**

## §13 Fix (j), the last one this lane had budget for

`culture_name_lists.cpp:169: Name list name_list_fae_X has only 0 dynasty names
defined, which is less than MINIMUM_DYNASTY_NAMES` — **838 lines, one per name
list, in every attempt from 2 to 6**. `MINIMUM_DYNASTY_NAMES = 2`
(`common/defines/00_defines.txt:1145`).

Game setup is exactly when CK3 needs one: it generates characters and mints a
dynasty for them, and the name comes from the name list. With an empty list
there is nothing to index.

CK2 keeps dynasty names globally in `common/dynasties`, each block carrying a
`culture`; CK3 keeps them per name list. So step `dynasties` now runs **before**
`cultures` and hands over `ctx.data["dynasties"]["names_by_culture"]` (CK2
culture → its `dynn_fae_<id>` loc keys), and each name list takes its own
culture's keys, topped up from the **culture group** when the culture alone has
fewer than two — which is vanilla's own rule, stated in that define's comment:
"Dynasty names from the culture group will count".

Result: **396 of 419** cultures reach the minimum. The 23 that do not are the
animal and undead cultures (`horse`, `cat`, `bear`, `lich`, `vampire`,
`wraith`, `dracolich`, …) — CK2 defines no dynasty anywhere in those groups, so
there is nothing to convert and the step warns by name. 838 errors become 46.

This is the standing hypothesis for the game-setup crash. Whether it is *the*
cause is the first thing the next lane should measure: the class disappears from
error.log either way, so a single launch answers it.
